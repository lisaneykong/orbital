What am I setting up, and why?

Five things get configured, and only the first two are required to see real jobs. Each one below says what it is in plain words, exactly where to click to get it, what it looks like, and a button to check it actually works before you rely on it.

← Back to the install console Open the dashboard Printable cheat sheet

The short version: Supabase is the filing cabinet that holds the jobs. GitHub is the robot that goes out every morning at 6am, reads company job boards, and puts what it finds in the cabinet. Your browser only ever reads from the cabinet — it never scrapes anything itself, which is why the site stays fast and works on your phone.

The two required keys

1

Supabase Project URL

The address of your filing cabinet

Required
What it is
The web address of your own Supabase project. Every job the scraper finds is stored there, and the dashboard reads from it. One project, one URL, and it never changes.
Where to click
supabase.com→your project→Settings→Data API→Project URL
https://sgjzwyyhjlfpleaclata.supabase.co
Watch out for
No trailing slash, and no /rest/v1 on the end. Just the bare address.
2

Supabase anon public key

The read-only pass your browser carries

Required
What it is
A long key that lets a browser read the jobs table and nothing else. It is designed to be public — it ships inside the page, and anyone can see it. That is fine and expected: it cannot write, delete, or read anything private.
Where to click
supabase.com→your project→Settings→API Keys→anon / public
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJpc3M…  (or)  sb_publishable_…
Watch out for
Do not paste the service_role key here. That one can rewrite your whole database, and this value is visible to anyone who views the page.

The scraper's own key

This one never touches your browser. It lives in GitHub's secret store, where only the scraper can read it.

3

Supabase service_role key

The write key — GitHub holds it, you never paste it into the site

Required for daily scraping
What it is
The key that can write to the jobs table. The scraper needs it to save what it finds. It is a full-access credential, so it goes in exactly one place: GitHub repository secrets.
Where to get it
supabase.com→Settings→API Keys→service_role(click reveal)
Where to put it
your GitHub repo→Settings→Secrets and variables→Actions→New repository secret
Name it exactly
SUPABASE_SERVICE_ROLE_KEY — and add a second secret named SUPABASE_URL holding the same URL from step 1.
Never paste this key into this website, the setup console, or any field in your browser. If it ever ends up in a page, anyone who visits can rewrite your database. Rotate it in Supabase if that happens.
sb_secret_…  (or a long eyJhbGci… JWT whose role reads "service_role")
How you know it worked
Open your repo's Actions tab, run Orbital daily scrape by hand once. The first step checks both secrets and says in plain English if either is missing or is the wrong kind of key.

Two optional extras

4

The trigger-scrape Edge Function

Makes the dashboard's "Refresh roles" button able to start a real scrape

Optional
What it is for
The 6am run happens on its own. But if you want Refresh roles to kick off a fresh scrape on demand, something has to ask GitHub to start one — and that request needs a GitHub token. This small function holds that token inside Supabase, so it never has to sit in your browser.
What you run, once
npm i -g supabase
supabase login
supabase link --project-ref <your-ref>
supabase secrets set GITHUB_TOKEN=… GITHUB_REPO=you/orbital ORBITAL_PIN=1725
supabase functions deploy trigger-scrape
The GitHub token it needs
A fine-grained token scoped to this one repository, with a single permission: Actions → Read and write. Nothing else. Make it at github.com/settings/personal-access-tokens.
If you skip this
Refresh roles still re-reads the database and picks up anything new. It just cannot start a scrape itself, unless you use option 5.
5

A GitHub token in the browser

The fallback if you would rather not deploy the function

Optional
What it is
The same fine-grained token as above, pasted into Settings → Live scraping on the dashboard instead of into Supabase. It is stored in that browser only and never leaves it except to call GitHub.
The honest tradeoff
Anyone who can use your computer can read it out of browser storage. Scope it to the one repo with only Actions write, and it can do nothing except start your scrape. On a shared machine, prefer option 4.
Where it goes
dashboard→Settings→Live scraping→Fine-grained token

Once it is all connected

The scrape runs at 6:00 AM Central every day on GitHub, whether or not anything is open. It writes its progress as it goes, so the dashboard can show you which job boards have reported back while a run is in flight. If a run fails, open the Actions tab and read the first red step — every check in that workflow is written to tell you what is wrong in words, not a stack trace.

Order of operations

1In Supabase, open SQL Editor and run the schema from the install console. Expect "Success. No rows returned".
2Put the Project URL and anon key into the install console. The dashboard now reads live data.
3In the GitHub repo: Settings → Secrets and variables → Actions. Add SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY.
4Actions tab → Orbital daily scrape → Run workflow. Read the first step's output; it names any bad secret in plain English.
5Optional: deploy the trigger-scrape function so Refresh roles can start a scrape on demand.

Good to know

Schedule6:00 AM America/Chicago daily. Two UTC slots are scheduled and a gate step lets only the correct one through, so daylight saving does not shift it.
Refresh rolesAsks GitHub for a fresh run, then watches the scrape_runs and scrape_progress tables and loads the new roles when it finishes.
If a run failsActions tab → the failed run → first red step. The secret checks report the actual problem.
"permission denied for table jobs"A missing GRANT, not row-level security. Run the isolated GRANT block from the install console.
Key safetyanon key public by design. service_role key never in a browser — rotate it in Supabase if it leaks.
