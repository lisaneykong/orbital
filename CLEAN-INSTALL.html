Clean install — build 17

Six steps, in order. Everything is a browser click; nothing here needs a command line. Budget about twenty minutes. Tick each step as you go — the ticks are saved in this browser, so you can close the page and come back.

STOP

Step 1 deletes every job currently in your database. That is the point of a clean install and the jobs are all re-scrapable, but it is irreversible. If you want to keep the current rows, open Supabase → Table Editor → jobs → Export → CSV before you start. Your saved roles, notes and applications live in a different table (user_state) and survive.

  1. Reset the databasesupabase.com

    One paste builds all four tables: jobs, user_state, scrape_runs, scrape_progress. The last two are the ones currently returning 404, which is why no scrape has ever been able to tell you which job boards failed.

    • Open SUPABASE-SCHEMA.sql from this kit in any text editor, select all, copy
    • Go to supabase.com/dashboard and open your Orbital project
    • Left sidebar → SQL Editor
    • Click + New query
    • Paste, then click Run (or Ctrl/⌘ + Enter)

    Stay on the same Supabase project. orbital-config.js already points at it, so a brand-new project would mean editing that file and re-deploying.

    Expect

    Success. No rows returned.

  2. Confirm the four tablessupabase.com

    Thirty seconds, and it is worth it. If scrape_runs is missing, the scraper's self-healing retry stays switched off without saying so, and the diagnose run in step 6 has nowhere to write its findings.

    • Left sidebar → Table Editor
    • Open the table dropdown at the top of the list
    • Check all four names are there: jobs · user_state · scrape_runs · scrape_progress

    If any are missing, step 1 did not finish — scroll up in the SQL Editor and read the red error. jobs should exist and be empty.

    Expect

    Four tables. jobs shows 0 rows.

  3. Push build 17 to GitHubgithub.com/lisaneykong/orbital

    Upload the contents of the ORBITAL-v17 folder to the top level of the repo, not the folder itself. Same-named files are replaced; your commit history is kept.

    • Repo home → Add file → Upload files
    • Drag in everything inside ORBITAL-v17
    • Commit message: build 17 — clean install → Commit changes

    Then two checks that matter more than they look:

    • Is there a resolved_tokens.json at the repo top level? If yes, open it → trash icon → Commit changes. The scraper trusts that cache and skips re-probing, so a stale copy pins companies to dead job-board tokens and returns zero roles forever. It is ignored by .gitignore now, but that does not remove a file already committed.
    • Open .github/workflows/. There should be exactly two files: scrape.yml and deploy.yml. Delete any others — an old workflow left behind keeps running on its own schedule and fights this one.
    Expect

    A new commit listing ~48 changed files, and exactly two workflow files.

  4. Check the secretsgithub.com → Settings

    These carry over from before, so this is a verification pass, not a re-entry. You cannot read a saved secret back — if you are unsure about one, overwrite it.

    • Repo → Settings → Secrets and variables → Actions
    • Required: SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY
    • For auto-publishing to IONOS: IONOS_FTP_SERVER · IONOS_FTP_USERNAME · IONOS_FTP_PASSWORD
    !

    The single most common failure. SUPABASE_SERVICE_ROLE_KEY must be the service_role / sb_secret_ key, not the anon / publishable one. The anon key can only read, so the scraper finds jobs and then silently has nothing to write them with. Supabase → Settings → API Keys → reveal service_role. The workflow checks this before it runs and says so in plain English.

    Expect

    Two secrets minimum, five if IONOS publishes itself.

  5. Upload to IONOSjobs.lisaney.com

    Skip this entirely if the three IONOS secrets are set — the deploy workflow publishes on every push, and step 3 already triggered it. Do it by hand only if you would rather not rely on that.

    • Turn on show hidden files in your FTP client first
    • Upload the contents of ORBITAL-v17 into the web root — not the folder itself
    • Confirm .htaccess arrived. Without it the site serves stale cached HTML and you will think the upload failed
    • Overwrite when prompted. Leaving old extra files behind is harmless; they just become dead URLs

    Open MANIFEST.txt to check nothing was dropped. It flags the four hidden files most upload tools skip.

    Expect

    jobs.lisaney.com → Settings shows build 2026-09-28.1.

  6. Run diagnose, then read the loggithub.com → Actions

    Diagnose before full. It probes one endpoint per job-board family plus a Supabase read and write, in under a minute, and it is the run that will finally say what the 39 Workday boards are doing.

    • Repo → Actions tab
    • Left sidebar → Orbital daily scrape
    • Right side → Run workflow
    • Change mode from full to diagnose
    • Green Run workflow → wait ~15s → refresh → click the new run at the top
    • Click the scrape job → expand Run scraper

    Scroll that log to the workday lines. You are looking for one of three things: no data-center subdomain answered, host answers but no board variant matched, or an HTTP 401 / 403 / 404. Each points at a different one of the three tokens.

    At the bottom of the run summary, if an Artifacts box shows failed-scrapes-log, download it — that CSV is the per-company failure list.

    When diagnose looks healthy, run it again with mode full to fill the board.

    Expect

    Green run, per-family results printed, and a first row in scrape_runs.

Send me the log

Paste the Workday lines from step 6, or attach failed_scrapes_log.csv. That turns "39 boards, zero rows" into named causes, and I can correct the tokens from it.

  • A clean install does not fix the Workday tokens. 21 of the 39 boards carry guesses marked unverified in companies.json. This install gives the scraper somewhere to record what happens to them; the repair comes from the log.
  • If the 18 verified boards return rows and the 21 do not, it is purely bad tokens and I fix them by hand.
  • If all 39 stay at zero, the cause is upstream of routing — the family failing before its loop, or rows being rejected on write — and I would look at the location filter next, since a role only survives if it maps to Seattle, Greater LA, New Zealand or US Other.
